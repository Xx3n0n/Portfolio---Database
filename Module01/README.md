# Module 1

## Learning Goals

By the end of this module, you can:
1. Explain how this class works — the CBL/PBL philosophy, the portfolio-based **project work** assessment, and the "moving bar" of a first-time course.
2. Set up your personal GitHub portfolio from the course template, with a clean first commit and a `.gitignore` that keeps databases and secrets out of Git.
3. Set up the entire toolchain reproducibly with **`uv`** — one fixed Python plus SQLite, DuckDB, Datasette, and more — on Windows, macOS, or Linux, and verify it.
4. Explain — with a measurement, not a slide — the difference between an **embedded** database and a **client/server** database, and why most local apps should not run a server.
5. Load real rows into SQLite and query them from Python using **bound parameters**.
6. Take a first LLM-generated query, run it, and begin the habit that defines this course: **verify before you trust**.

# Reflections

## 1. First Impressions and Overall Experience

The introductory module for the Database class from Prof. Unger was definitely something. If I had to describe it in one word, I would say *different*. This approach to teaching and learning is quite novel to me, and the experimental nature of the module's design has been challenging to adapt to, yet in many ways, it is also fun and exciting.

In retrospect, I feel that the difficulty of adapting to so many new concepts at once might have been underestimated. Many of my peers had never interacted with GitHub before, which made it difficult to get started with the learning process. However, by the end of the session, I think most of us had at least started to get the hang of it.

For me personally, I often felt that while I was still figuring out how to do one thing, the class had already moved on to the next. With the help of my podmates and some much-needed guidance from the professor, I was eventually able to catch up. All in all, it was a lot to take in.

## 2. Challenges Faced

One of my biggest challenges was setting up my development environment. Although creating a repository from the provided template was relatively straightforward, cloning it into VS Code simply would not work. After a lot of trial and error, I even switched my IDE to Zed, but I still couldn't get it working during the session.

I eventually resolved the issue at home after doing some research and getting help from AI. The solution was surprisingly simple: I needed to install Git on my system and then clone my repository using the appropriate command. Looking back, it was a relatively small issue, but it took up a considerable amount of time because I lacked familiarity with the tools.

Another challenge was keeping up with the pace of the class. While I was still trying to understand one concept, we were already moving on to another. This made it difficult to absorb everything during the session, especially when several unfamiliar tools and concepts were being introduced simultaneously.

## 3. What I Learned

The first task gave me my first real introduction to GitHub. Before this class, I had never really used the platform, and I genuinely thought a *repo* was some kind of lizard! Creating my first repository and making my first commit was a small but satisfying milestone.

I also learned about the purpose of a `.gitignore` file and why it is important to keep certain local files and sensitive information out of a repository.

Another small lesson came from my first commit. I accidentally included typos in my portfolio description and used the commit message `Updated Portfolio Description` instead of `Update Portfolio Description`. Although this was a minor mistake, it made me pay more attention to commit message conventions and the importance of maintaining a clear and understandable project history.

During the second task, I became more familiar with Git and my IDE. The process of making changes, committing them, and pushing them to GitHub started to feel more manageable. I also began to understand that Git is not simply a tool for uploading files, but a way to track changes and maintain an organized workflow.

## 4. Collaboration and Independence

Forming the task pod was quick and easy. I had worked with Ian and Arshia on previous projects, and I feel that we have good chemistry and complement one another well.

However, Ian generally takes the lead when it comes to technical knowledge. During our previous semester's OOP class, we felt that we had become too dependent on him. One of our main goals this time around is to become more independent and figure out more things ourselves while maintaining a collaborative spirit.

During the introductory tasks, I received help from my podmates and the professor, which was valuable in helping me catch up. At the same time, having to troubleshoot my Git setup independently at home forced me to research the problem and work towards a solution myself.

Although I would have preferred to solve the issue during class, the experience helped me develop my problem-solving skills and become more comfortable with my own workflow.

## 5. What Could Have Gone Better

Ideally, I would have liked to resolve my setup issues during class and complete the tasks at the intended pace. Having my podmates and professor readily available would have made it easier to ask questions, understand the solutions, and continue learning alongside everyone else.

Instead, I had to finish some of the work at home, where immediate help was not readily available. While this encouraged me to become more independent, it also meant that I missed out on some of the collaborative learning opportunities available during class.

In future sessions, I would like to get my development environment working as early as possible so that technical setup issues do not interfere with the actual learning process.

## 6. Overall Progress and Next Steps

Compared to the first task, I feel that I have become more comfortable navigating GitHub and using my IDE. Although I still have a lot to learn, the basic workflow is beginning to make more sense, and I am less intimidated by the tools than I was at the beginning.

I also recognize that becoming proficient with these tools requires practice rather than simply following instructions once. Going forward, I want to become more confident in troubleshooting problems independently, understand the reasoning behind the steps I take, and contribute more actively to my pod's work.
